# 核心数据结构与算法

FreeRTOS-Kernel 的实现并不依赖复杂容器。它反复使用少量基础结构来完成调度、阻塞、唤醒和超时管理。理解这些结构后，阅读 `tasks.c`、`queue.c`、`timers.c` 会容易很多。

## 双向环形链表

`List_t` 是 FreeRTOS 最核心的基础设施。它是带哨兵节点的双向环形链表，哨兵节点 `xListEnd` 永远存在，空链表时它的前后指针都指向自己。

`ListItem_t` 是挂入链表的节点。每个节点有三个重要信息。

`xItemValue` 用来排序。延时列表中它通常是唤醒 tick；事件等待列表中它常被编码成任务优先级；定时器列表中它是到期时间。

`pvOwner` 指向拥有这个节点的对象。任务状态列表里通常指向 TCB，定时器列表里通常指向 Timer 控制块。

`pxContainer` 指向当前所在链表。移除节点时可以通过它快速知道自己在哪个链表里。

FreeRTOS 用同一套链表表达多种含义，区别只在于 `xItemValue` 的解释和 `pvOwner` 指向的对象。

## 有序插入与轮转插入

链表有两类常见插入方式。

`vListInsert()` 按 `xItemValue` 从小到大插入。延时任务和软件定时器常用这种方式，因为越靠前越早到期。事件等待列表也利用排序，让最高优先级等待者更容易被选出。

`vListInsertEnd()` 插入到链表末尾附近。就绪列表常用这种方式。同一优先级的任务拥有相同调度优先级，放到末尾后，调度器可以通过 `listGET_OWNER_OF_NEXT_ENTRY` 在它们之间轮转。

## 就绪列表

调度器维护一个按优先级分桶的数组：`pxReadyTasksLists[]`。数组下标就是任务优先级，每个元素是一条任务链表。

当任务变为就绪时，内核把它的 `xStateListItem` 插入对应优先级链表，同时更新最高就绪优先级记录。

选择下一个任务时，调度器先定位最高的非空优先级链表，再从该链表取下一个 TCB。同优先级任务通过链表游标轮转，避免一个任务长期占用同优先级执行机会。

## 最高优先级选择

FreeRTOS 有两种选择最高就绪优先级的方式。

通用方式使用 `uxTopReadyPriority` 记录当前可能的最高优先级。如果该优先级链表为空，就向低优先级扫描，直到找到非空链表。

移植层优化方式由 `configUSE_PORT_OPTIMISED_TASK_SELECTION` 启用。此时 port 可以维护位图，并用 CPU 指令快速找最高置位。例如某些处理器可以用 CLZ 类指令把“找最高优先级”变成常数时间操作。

通用方式更可移植；port 优化方式更快，但依赖具体架构支持，并受配置限制。

## 延时列表与 tick 回绕

任务延时不能简单地只用一张按到期 tick 排序的链表，因为 `TickType_t` 会回绕。例如 32 位 tick 达到最大值后会回到 0。

FreeRTOS 使用两张延时列表解决这个问题。

`pxDelayedTaskList` 保存当前 tick 周期内会到期的任务。

`pxOverflowDelayedTaskList` 保存到期时间跨过 tick 回绕点的任务。

当 tick 回绕时，两张列表交换角色。这样比较到期时间时，大部分情况下仍然可以用简单的数值顺序。

`xNextTaskUnblockTime` 记录当前延时列表中最早的唤醒时间。tick 中断只需要先比较当前 tick 是否达到这个值，达到后再处理链表头部连续到期的任务。

## 事件等待列表

队列、信号量、事件组等对象都需要记录“哪些任务正在等我”。这类等待通常通过任务的 `xEventListItem` 实现。

队列内部有两条事件等待列表。

`xTasksWaitingToSend` 记录因为队列满而等待发送的任务。

`xTasksWaitingToReceive` 记录因为队列空而等待接收的任务。

这些列表按等待任务优先级排序。条件满足时，内核可以直接从列表头部取出应该最先唤醒的任务。

事件组的等待更复杂，因为任务可能等待任意一个 bit，也可能等待所有 bit，还可以要求退出等待时清除 bit。因此事件组会把等待条件编码到事件节点的值里，并在 bit 改变时测试哪些任务满足条件。

## 队列环形缓冲区

普通队列把每个元素按值复制进内部存储区。`pcHead` 指向队列存储区开始，`pcWriteTo` 指向下一次写入位置，`pcReadFrom` 指向上一次读取位置，`pcTail` 用作尾部边界。

发送时，数据被复制到写指针位置，写指针前进并在尾部回绕。接收时，从读指针的下一个位置复制数据，读指针前进并回绕。

这种设计使队列元素生命周期独立于发送方变量。发送方传入的是数据地址，但队列保存的是数据副本，而不是指针本身。

## 队列锁与 ISR 协作

队列有 `cRxLock` 和 `cTxLock` 两个锁计数字段。它们不是普通互斥锁，而是用于协调“队列正在被任务上下文操作时，ISR 又修改了队列”的情况。

当队列被锁定时，ISR 仍可以放入或取走数据，但不会立即修改事件等待列表。它只增加锁计数，表示解锁时可能需要唤醒任务。

任务上下文解锁队列时，会检查这些计数，再统一处理应该解除阻塞的任务。这样可以减少在敏感路径中直接操作复杂链表的风险。

## 软件定时器列表

软件定时器也使用两张列表：当前定时器列表和溢出定时器列表。思想与任务延时列表类似，都是为了处理 tick 回绕。

Timer 服务任务只允许自己访问这些列表。其他任务不直接操作定时器列表，而是向定时器命令队列发送命令。服务任务收到命令后再启动、停止、重置或修改定时器。

到期时间最近的定时器位于列表前部。服务任务可以根据下一个到期时间决定自己阻塞多久，同时也能被命令队列中的新消息提前唤醒。

## 内存块链表

`heap_4.c` 和 `heap_5.c` 使用空闲块链表管理堆。每个空闲块前面有一个块头，记录块大小和下一个空闲块。

释放内存时，堆实现会尝试把相邻空闲块合并，减少碎片。`heap_4.c` 适合一个连续堆区域，`heap_5.c` 支持多个不连续堆区域。

`heap_1.c` 没有释放能力，算法最简单。`heap_2.c` 可以释放但不合并相邻块。`heap_3.c` 直接包装 C 库的 `malloc()` 和 `free()`。

## 核心算法的共同特征

FreeRTOS 的核心算法偏向确定性和低开销。它避免通用动态容器，尽量用固定结构、宏和链表节点完成工作。

这种风格带来的结果是：代码读起来需要理解很多宏和条件编译，但运行时开销低，且容易让移植层针对具体硬件做优化。
