# 移植层与内存管理

FreeRTOS-Kernel 的公共内核代码尽量不直接依赖某个具体 CPU。与硬件相关的部分放在 `portable/` 目录中，与动态内存相关的策略放在 `portable/MemMang/` 中。

## 移植层的职责

移植层负责把内核需要的底层动作映射到具体处理器、编译器和中断模型。

主要职责包括：

1. 初始化任务栈，使任务第一次被调度时能像普通函数一样开始运行。
2. 启动调度器，并配置产生系统 tick 的硬件定时器。
3. 在 tick 中断或主动 yield 时触发上下文切换。
4. 保存当前任务上下文，恢复下一个任务上下文。
5. 实现临界区进入和退出，保护内核共享数据。
6. 定义中断安全 API 可以使用的最高中断优先级规则。
7. 提供架构相关的类型、栈增长方向、对齐要求和优化宏。

公共内核通过 `portYIELD_WITHIN_API()`、`portYIELD_FROM_ISR()`、`portENTER_CRITICAL()`、`portEXIT_CRITICAL()`、`vPortStartScheduler()` 等接口表达需求，具体实现由对应 port 提供。

## port 目录如何选择

`portable/` 下通常按编译器和架构分层。例如 `portable/GCC/ARM_CM4F/` 表示 GCC 编译器下 Cortex-M4F 的移植实现。

一个应用工程不会编译所有 port。它只选择与目标芯片和工具链匹配的那个 port，再配合公共内核文件一起构建。

典型 port 目录包含：

`portmacro.h` 定义移植层宏、基础类型、临界区宏、yield 宏和架构相关配置。

`port.c` 实现调度器启动、tick 配置、上下文切换辅助和中断处理入口。

汇编文件用于完成 C 语言不方便或无法直接表达的寄存器保存恢复、异常返回和特殊指令序列。

## 临界区与中断

FreeRTOS 内核会频繁修改共享结构，例如就绪列表、延时列表和队列等待列表。这些操作必须避免被中断或其他核心并发破坏。

在单核 MCU 上，临界区通常通过屏蔽一定优先级以下的中断实现。这样内核可以保护自己的数据，同时仍允许更高优先级、不会调用 FreeRTOS API 的中断运行。

在支持中断优先级的架构上，`configMAX_SYSCALL_INTERRUPT_PRIORITY` 这类配置非常关键。能够调用 FreeRTOS `FromISR` API 的中断优先级必须符合 port 的约束，否则可能破坏内核临界区假设。

在 SMP 系统上，除了中断屏蔽，还需要处理多个 core 同时访问内核状态的问题。相关 port 和调度器会配合使用锁、core id、跨核 yield 请求和任务运行状态字段。

## tick 与上下文切换

tick 中断推动内核时间前进。每次 tick 到来，内核检查延时任务是否到期，处理时间片轮转，并判断是否需要切换任务。

上下文切换本身是移植层最核心的工作。它需要保存当前任务的 CPU 寄存器到当前任务栈或 TCB，再从下一个任务恢复寄存器和栈指针。

在 Cortex-M 这类架构上，常见做法是利用 PendSV 等异常完成延后切换。在其他架构上可能使用软件中断、陷入指令或手写汇编入口。

## 动态内存接口

FreeRTOS 的动态对象创建 API 最终依赖两个函数：

`pvPortMalloc()` 申请内存。

`vPortFree()` 释放内存。

这些函数不是由 C 标准库直接强制提供，而是由选中的 heap 实现提供。应用可以使用 FreeRTOS 自带的 `heap_1.c` 到 `heap_5.c`，也可以在特殊项目中提供自己的实现。

如果项目禁用动态分配，只使用静态创建 API，那么可以不依赖堆分配路径。但许多常见 API，例如动态创建任务、队列和定时器，都需要 `pvPortMalloc()`。

## heap_1

`heap_1.c` 只支持分配，不支持释放。它实现简单，碎片问题最小，因为内存只向前消耗。

它适合系统启动时一次性创建所有对象，运行过程中不删除任务、不删除队列、不释放动态对象的项目。

缺点是不能回收内存，不适合对象生命周期复杂的应用。

## heap_2

`heap_2.c` 支持释放，但不会合并相邻空闲块。

它适合分配和释放块大小比较固定的项目。如果分配大小变化很大，长期运行后可能出现碎片，导致总空闲内存足够但无法分配连续大块。

现代项目通常更倾向于使用 `heap_4.c` 或自定义 allocator。

## heap_3

`heap_3.c` 包装标准 C 库的 `malloc()` 和 `free()`。

它把内存策略交给编译器运行库和链接器堆配置。优点是实现简单，容易与已有系统堆集成。缺点是确定性、线程安全和堆大小行为取决于 C 库和平台配置。

## heap_4

`heap_4.c` 是常用实现之一。它管理一个连续堆数组，并在释放时合并相邻空闲块，从而降低碎片。

每个块有块头记录大小和链表信息。块大小字段的最高位用于标记该块是否已分配。空闲块按地址顺序链接，释放时可以检查前后相邻块是否也空闲，并合并成更大的空闲块。

它适合大多数只有一个连续 RAM 堆区域的嵌入式项目。

## heap_5

`heap_5.c` 与 `heap_4.c` 思路相近，也会合并相邻空闲块，但它支持多个不连续内存区域。

应用需要调用 `vPortDefineHeapRegions()` 提供这些区域。它适合 MCU 有多段 RAM，或者不同 RAM bank 需要共同作为 FreeRTOS 堆使用的场景。

区域必须按地址顺序提供，且在首次分配前完成定义。

## 静态分配与动态分配

FreeRTOS 支持静态分配和动态分配。静态分配由应用提供对象控制块和栈缓冲区，内核只初始化这些内存。动态分配由内核调用 `pvPortMalloc()` 申请对象所需内存。

静态分配更可控，适合安全性、确定性和认证要求高的项目。动态分配更方便，适合对象数量和生命周期更灵活的项目。

很多系统会混合使用两者。例如 Idle 任务和 Timer 服务任务使用静态分配，普通业务对象使用动态创建。

## 选型思路

如果项目不允许运行时释放对象，`heap_1.c` 简单且确定。

如果需要释放对象，并且只有一个连续堆区域，优先考虑 `heap_4.c`。

如果有多个不连续 RAM 区域，希望统一交给 FreeRTOS 堆管理，考虑 `heap_5.c`。

如果项目已有成熟系统堆，并且能够保证线程安全和实时性，才考虑 `heap_3.c`。

无论选择哪种堆，内核调度逻辑和内存分配逻辑都是分离的。调度器只关心任务和对象已经存在后的状态变化，堆实现只负责给动态对象提供存储空间。
